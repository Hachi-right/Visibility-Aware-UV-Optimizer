项目大脑说明

这份 HTML 是完整设计审阅页；同一套设计指导思想和说明正文已落盘到 项目大脑/说明.md。日常启动不要全文加载它，只从 项目大脑/启动.md 进入；启动完成后先读 项目大脑/主流程.md 获取公共加载顺序，再读取公共 index.md 与 项目大脑/主流程.md §2 硬规则速查（不读主规则全文），随后进入当前用户 私有流程.md / 私有规则.md，再加载当前任务上下文；私人索引、职责、软上下文和经验主题只在触发场景下按需查询。

目标定位：团队的目标是用 AI 提升协作与交付效率。项目大脑、代码规范和验收体系，是把这个目标落到每天协作里的基础设施。

为什么现在必须做

项目大脑不是为了多建几份文档，而是为了应对 AI 协作进入规模化之后的系统性压力：代码库变大、任务并行变多、上下文越来越装不下，光靠聊天记录和全局搜索已经很难稳定接住项目。

换句话说，这不是在做小优化，而是因为 AI 协作规模化后，团队需要一套可恢复、可验证、可交接的上下文基础设施。

Agent 写得越快，项目不一定越可控

当项目越来越大时，code agent 会越来越依赖长时间搜索和局部猜测。它明明很卖力，但代码库越大、低可预测代码越多，它就越看不懂、越搜不准；搜不到已有能力，就继续重复造轮子，代码又进一步膨胀，形成恶性循环。

同时，AI 越来越容易跑偏：AI 如果看不到人类的设计思路，或者没有正确检索到相关文档，就会开始乱脑补，把需求边界越扩越大，混淆概念。结果可能是交付方向完全错误，或者擅自加很多没有要求的特性，让代码失控膨胀，产出不符合要求。

AI 干活越来越慢不是它不努力，而是项目越大、代码越乱，它越看不懂、越搜不出来，最后靠猜和重写继续堆高复杂度。
AI 越来越容易跑偏它看不到设计思路，或没有正确检索到相关文档时，就会靠脑补扩展需求边界，混淆概念，做出方向错误或堆满未要求特性的结果。
并行开发容易冲突多人、多 worktree、多 AI 会话同时推进时，如果没有共同任务状态和边界，改动很容易互相覆盖。
职责边界不清晰 容易提交冲突AI 不知道当前使用者负责什么，就可能到处改；使用者本来也不负责那块，自然看不懂，只能被迫提交，最后和别人冲突，甚至破坏设计思路。
“完成了”不等于测过AI 不知道怎样理解用户的真实验收标准，就会自己脑补检查项。它说完成了，往往只是它以为完成了，人类还要花时间纠偏。
经验留在聊天里不切窗口也会有上下文压缩；一压缩，很多判断和踩坑信息就丢了，后面继续重复踩坑，甚至做出和旧决策矛盾的新判断。

这个系统解决什么问题

项目大脑不是为了写更多文档，而是为了让这些已经暴露出来的问题有稳定解法。它让人和 agent 都能高预测性地知道公共规则在哪里、当前用户是谁、当前 worktree 正在做哪个任务、职责边界在哪里、验收证据应该写到哪里。

AI 越来越慢

用代码规范、索引和任务记录减少全局搜索、低效猜测和重复造轮子。

AI 容易跑偏

把设计思路、术语、规则和业务边界放进稳定入口，减少 AI 检索不到文档后乱脑补、扩需求边界和擅自加特性的机会。

并行开发冲突

公共规则和个人过程分开，任务过程按 task 隔离，多 worktree 不共用临时状态。

职责边界不清

每个 author 先加载自己的职责范围，越界请求先拒绝并说明风险，用户坚持时先确认是否修改边界。

完成不等于测过

验收流程按改动范围触发功能验证和证据回写，不让 AI 自己脑补完成标准。

经验留在聊天里

过程、决策、指标和可复用经验落到任务目录或公共区，减少压缩后反复踩坑。

核心原则

  • AGENTS.md 是仓库统一入口和轻量导航页；先引导项目大脑，再给出项目概述、常用目录和重要文档索引。
  • docs/agent工作规则.md 承载项目背景、架构图、开发命令和数据表规则，按需阅读，不作为第二套启动入口。
  • 项目大脑/启动.md 是实际冷启动入口；它拉起 主流程.md，而 主流程.md 只说明加载完成后的文档加载顺序，不反向索引或解释入口文件。
  • 说明.md 是设计指导思想和 Markdown 说明正文，说明.html 只用于完整设计审阅。
  • 所有 author 都不能直接修改其他 author 的私人用户区；跨角色规则由对方确认后装载到自己的私人区。
  • 新建 skill、MCP、hook 和辅助落盘默认先放当前 author 私有区；公共扩展目录只保存 leader 公共化后的团队共享能力。
  • 每个用户区有且只有一个一级目录索引：项目大脑/用户/{author}/index.md。
  • 冷启动检查由 project-startup-check 用 Python 执行；缺用户目录或当前 author 私有扩展目录时，由它调用对应 skill 补齐，不让 agent 临场手工挑文件创建；启动输出必须让用户核对 author、用户描述、任务目录和任务摘要。
  • 冷启动时在仓库根使用 workstate.json 指向当前 author 和当前任务文件夹；project-startup-check 读取和校验它，这个文件不入库。
  • 新会话、上下文压缩后、长时间运行后和任务恢复后，必须先重新读取当前任务文件和当前 author 私有流程/规则，稳定目标、决策、范围和约束；项目级 session/compact/长会话 hook 只负责提醒或在工具支持时注入重载提示，不替代真实读取。
  • 推分支或推 main 前使用 perfect-push，先证明 origin/main 是当前 HEAD 的祖先，再审查将入库的提交和 diff stat。
  • 需求很大、边界不清、跨模块或评估复杂时，先梳理目标和边界，查相似实现，拆阶段、定每阶段验收，再一阶段一阶段推进。
  • 流程和规则文档要短、准、无歧义；主流程.md 只写加载顺序，主规则.md 写规则正文和工件职责，细节交给对应文件或 skill。
  • 多级索引拆解和归类是一套通用方法论；公共和私人一级 index.md 只做入口，经验、公理、代码地图、资料地图、会议资料和设计资料也按同一原则分级归类。
  • 搜索代码、调研相似功能、定位入口或评估复用前，先使用 project-code-map 查当前 author 私人 代码地图/ 和 差异列表.md，再查公共 代码地图/；读完地图后产出查询规划卡，再带地图锚点用 CodeGraph / 限定目录 rg 验证。
  • 搜索文档、配置、脚本、表格、静态资源、会议记录、设计思路或外部资料前，先使用 project-search-map 查当前 author 私人 资料地图/，再查公共 资料地图/；普通搜索后只写当前 author 私人资料地图。
  • 公共 主流程.md / 主规则.md 只管团队共享层；公共层加载完后进入当前 author 的 私有流程.md / 私有规则.md，再加载当前任务上下文；私人 index.md 是大索引，只在需要私人文献、经验、职责或软上下文时按需查询。
  • 个人中间产物、实验记录、精选证据放在 项目大脑/用户/{author}/ 下；设计指导思想、说明正文和完整设计审阅页保留在根目录 项目大脑/说明.md / 项目大脑/说明.html。
  • 不保留 _template 目录；project-startup-check 只编排启动检查，用户基础结构由 init-project-info-user 生成，当前 author 私有扩展目录由 project-info-extension-standards 生成，具体任务目录由任务 skill 生成。
  • 借鉴“预制菜”的公理、灵魂、沟通、用户习惯结构，但只借鉴结构，不复制其私人内容。
  • 公共软上下文只放项目级判断原则目录 公理/；其中 index.md 按场景指向主题公理文档，公理按主题聚类追加，不一条公理一个文件；协作灵魂.md 和 沟通规范.md 放在每个 author 私有用户区。
  • 私人 经验/ 是当前 author 的任务经验库和方法索引库；每个 author 的经验不同，不能互相默认替代；通过 summarize-private-experience 写入当前 author 主题聚类经验文档，并同步当前 author 私人 index.md；用户单独要求整理经验时先开独立临时整理任务，整理结果 push 到 main 后再清理临时任务，临时任务本身不 commit、不 push。
  • 整理前先加载私人整理经验和公共整理共识；整理后输出 整理确认.md 或 leader整理确认.md，请使用者校准重要/不重要的标准、关注点、措辞、结构、可读性技巧和模块理解方法。
  • 私人 代码地图/ 是当前 author 的代码定位知识库；每次搜索代码后，把稳定入口、关键符号和查找经验按主题写回，和公共地图不一致时同步私人 差异列表.md，后续由 leader 抽取公共代码地图。
  • 私人 资料地图/ 是当前 author 的项目资料定位知识库；每次搜索文档、配置、脚本、表格、静态资源、会议记录、设计思路或外部资料后，把稳定入口和查找经验按主题写回，后续由 leader 抽取公共资料地图。
  • 初始分工表.md 只用于初始化或人工修订个人 职责范围.md；日常修改边界以用户私有 职责范围.md 为准。
  • 用户请求突破当前 author 职责范围时，agent 先明确拒绝并说明风险；用户坚持时，先确认是否修改职责范围/修改边界，再记录风险并继续。
  • 当前 author 可以基于已达成共识的交付规则文档，主动要求项目大脑把允许目录、文件类型、脚本范围、禁止事项和风险同步到自己的私人 职责范围.md。
  • 个人静态角色规则、长期职责和默认修改边界统一写在 职责范围.md；不再新建第二个个人静态规则文件。
  • 跨角色约束、规范、共识、可用 skill 和修改边界先形成交付规则文档；执行方确认后，装载到自己的私人 index.md / 职责范围.md，长期有效。
  • 外部资料入库时按项目约定整理到 docs/ 并写索引；会议清洗前先查 docs/会议转写术语表.md，只按人名、昵称和不常见易错词纠错。
  • tech-lead 是程序 leader，可以修改 项目大脑/启动.md、项目大脑/主流程.md 和 项目大脑/index.md；其他 author 不可以直接修改这三个文件。
  • 项目大脑/主规则.md 是受保护入口文件，Agent 修改前必须获得用户二次确认。
  • 项目大脑/工具经验.md 是系统工具经验入口；具体适用范围和写入规则以该文件为准。
  • 项目大脑/第三方辅助工具.md 是 CodeGraph、cc-artifact、agent compact/turn hook 能力边界和 agent MCP 适配等低频辅助能力入口；缺工具时优先开子 agent 安装或初始化。
  • 项目大脑/skills/project-startup-check/ 是冷启动检查入口；输出启动阶段、用户识别、任务识别和 next_action 后，再进入建 worktree、选任务、继续任务或读取当前任务。
  • 项目大脑/skills/project-validation/ 是任务验收入口。
  • 已公共化 skills 放在 项目大脑/skills/，新建 skills 默认先放 项目大脑/用户/{author}/skills/。
  • skills、mcps、hooks 的私有优先落点和 leader 公共化规则由 项目大脑/skills/project-info-extension-standards/ 管理。
  • author 是当前操作者的远程账号名或用户明确确认的稳定身份，不是仓库 URL 里的项目归属命名空间。
  • 项目大脑的结构、规则、skill、流程图、验收方式、设计指导思想或汇报内容发生稳定变更时，必须同步更新 说明.md 和本 说明.html。
  • 本机私有材料放在 项目大脑/用户/{author}/_local/ 或任务内 raw-local/，这些内容不入库。

主流程图

1入口校验

  1. AGENTS.md
  2. 启动.md
  3. project-startup-check

确认分支、workstate.json、author、用户区和当前任务指针。

2任务分流

  • 在 main/master 且要改文件：创建 worktree
  • 无任务：新建任务
  • 已有任务：继续或 fork

输出用户描述和任务目录，让人核对是否认错人或任务。

3公共加载

  1. 主流程.md
  2. index.md
  3. 主规则.md

团队共享规则、公共 skill、公共资料和 Markdown 工件职责在这里生效。

4私有加载

  1. 私有流程.md
  2. 私有规则.md
  3. process.md / design.md
  4. 任务范围.md / 任务指标.md

私人索引、职责范围、经验、软上下文、代码地图和资料地图按触发场景再读。

5执行收尾

  1. 按职责边界执行
  2. 按需查代码地图 / 资料地图 / docs
  3. 按 project-validation 验收
  4. 写回任务记录和私人知识

压缩后、长时间运行后、任务恢复后，从第 3 步重新加载并收敛目标。

读入

上下文从哪里来

  • 公共：index.md、主规则.md
  • 私人：私有规则.md、当前任务文件
  • 按需：职责范围.md、私人 index.md、经验、地图、docs
判断

当前要不要继续

  • 目标是否清楚
  • 职责是否越界
  • 是否已有相似任务或旧实现
  • 是否需要拆阶段
写回

结果落到哪里

  • 过程：process.md
  • 决策：design.md
  • 范围和证据：任务范围.md
  • 经验、代码地图、资料地图：当前 author 私人区

项目核心思想索引

本节只维护核心思想文档入口；具体设计内容以被引用文档为准。

代码规范索引

写代码、改名、调试、做防御式编程或评审代码时，先按下表读取稳定规范。把【示例业务域】 项目的代码规范接入项目大脑，是为了让代码自注释：看到名字就能大致猜到接口作用和变量类型，根据功能就能大致猜到相关代码的位置或最近查找入口，减少搜索接口的尝试次数，提高首次搜索成功的命中率。

减少搜索尝试

目录、模块、接口、变量和业务术语保持稳定规律后，agent 和人可以根据功能先猜到相关代码位置或最近查找入口，而不是每次全仓库扫一遍。

提高首次命中率

同一类功能使用同一套命名和路径，搜索词更容易第一次就命中关键入口、接口作用、变量类型、数据结构和流程节点，减少误入相似但无关代码的概率。

提高可预测性

代码路径、函数名、参数名、返回值和日志字段互相印证，出现问题后能沿固定路径推断关联模块和关键入口。

快速命中第一现场

防御式编程要求入口参数、外部 I/O、返回值和业务回调都做显式检查并输出有用日志，减少 bug 被吞掉或延后爆炸的机会，让调试更快落到问题源头。

这组索引服务于代码可预测性：代码位置、接口名、变量名、数据结构和错误日志都应能互相印证，让问题暴露在靠近源头的位置，而不是靠猜和大范围搜索排查。

工具经验索引

工具经验用于沉淀跨任务可复用的系统工具方法。本节只说明入口，不维护条目清单；具体适用范围、当前条目和写入规则以 工具经验.md 为准。

不在说明页复制当前已收录条目。需要查看或修改条目时，直接打开 项目大脑/工具经验.md。

第三方辅助工具

CodeGraph、cc-artifact、agent session/compact hook 和长会话 turn hook 这类能力是低频辅助能力，不进入冷启动主线。需要时先检测，已有就跳过；缺失时优先交给子 agent 安装或初始化，主流程继续推进。会话、压缩和长会话 hook 的能力必须按工具区分，不能把“有事件”误当成“能注入模型上下文”。

长会话提醒默认 30 轮触发一次，阈值不低于 20 轮；计数写入 .git/info/project-info-turn-reminder.json，不写 workstate.json，避免每轮把仓库弄脏或制造合并冲突。

CodeGraph 的项目索引生成在 .codegraph/，属于本机缓存，不入库。cc-artifact 只检测本机插件或 MCP 配置，不复制插件源码。

验收流程

任务收尾前按改动范围读取 project-validation。它把验收分成 lint、单元测试、端到端集成模拟和日志分析几层；私人测试 skill 只作为当前 author 的补充，不复制公共流程。

完整模拟不是只看启动成功。涉及核心业务链路时，要观察主链路输出、trace 或任务日志；涉及错误处理时，要确认业务错误可观察、框架错误带有用信息失败。

Leader 公共化流程

多人、多任务产生的经验先保留在各自任务目录。只有经过验证、能跨任务复用、且前因后果完整的内容，才由 tech-lead 或用户明确授权的维护者提升到公共区。leader 公共抽取每天最多一次，避免整理行为干扰主任务。

  1. 读取候选任务的 process.md、design.md、必要的 handoff.md 和验证记录，确认它不是一次性尝试。
  2. 按归属写入公共区：系统工具经验写 工具经验.md；第三方辅助工具适配写 第三方辅助工具.md；项目判断原则写 公理/ 对应主题文档；稳定代码入口和查找经验写 代码地图/ 对应主题文档；稳定资料入口和查找经验写 资料地图/ 对应主题文档；团队硬规则写 主规则.md；加载顺序变化才写 主流程.md；代码规范写 docs/代码规范.md 或术语表；公共能力写入 skills/、mcps/ 或 hooks/。协作灵魂.md 和 沟通规范.md 属于各 author 私人软上下文。
  3. 同步 项目大脑/index.md；如果内容只对某个 author 常用，只同步该 author 私人 index.md。
  4. 不复制私人任务流水到公共区；公共文档只保留稳定结论、适用场景、前因后果和必要来源线索。
  5. 把写入位置、来源任务和验证结果写回 leader 当前任务 process.md；形成稳定公共化决策时写入当前任务 design.md。
  6. 收尾前跑路径存在性、skill 校验和相关验收；改了入口、公共 skill 或本页时，重新跑覆盖测试。

改文件前闸门

当用户请求需要修改仓库文件时，项目大脑先执行闸门判断，避免直接把任务做在主线，或者把一个 worktree 的任务状态覆盖到另一个任务。

当前在 main/master

  1. 拒绝直接改文件。
  2. 根据用户要做的事生成任务分支名，建议带上 {author}、开始日期和任务 slug。
  3. 创建新的 worktree。
  4. 在新 worktree 中生成根目录 workstate.json。
  5. 在 项目大脑/用户/{author}/tasks/ 下创建具体任务子文件夹。
  6. 在任务文件夹里创建 process.md、design.md、任务范围.md 和 任务指标.md，并追加当前 author 的 tasklist.md。
  7. 告诉用户新 worktree 目录在哪里，建议用户在那个目录重新打开会话。

当前已经在任务分支

  1. 读取 workstate.json。
  2. 如果 task_folder 为空字符串，可以直接创建新任务子文件夹。
  3. 如果 task_folder 已经指向具体任务文件夹，且和用户新请求无关，必须先询问用户是否开启新任务。
  4. 用户同意后，创建新的任务目录，并把 workstate.json.task_folder 更新到新目录。
  5. 不要覆盖已有任务目录；任务目录名带开始日期，并在重名时追加序号。

目录与命名规则

目录和基础文件按创建职责分层，不由 agent 临场手工拼目录。完整逐文件规则以 项目大脑/主规则.md 为准，加载顺序以 项目大脑/主流程.md 为准。

冷启动核查由 project-startup-check 编排；用户基础结构由 init-project-info-user 一次性补齐，其中包含 私有流程.md、私有规则.md、skills/、mcps/ 和 hooks/；project-info-extension-standards 负责扩展内容的创建规范和公共化边界；具体任务目录由任务 skill 创建。项目大脑 skill 只在 项目大脑/skills/ 和 项目大脑/用户/{author}/skills/ 下查找，不把 skills/... 当作仓库根路径。新建 skill / MCP / hook / 辅助落盘默认先放当前 author 私有区；不要为每个子目录创建 index.md，不要把个人偏好猜出来写死，也不要把临时过程误归纳成公共规则。

author 识别规则

author 是项目大脑用户目录名的默认来源。它应该来自当前操作者的远程账号或用户明确确认的稳定身份。

origin = https://gitlab.example.com/{repo_owner}/example-repo.git
repo namespace = {repo_owner}
current operator author = {author}
  1. 普通冷启动优先读取根目录 workstate.json.author。这是当前 worktree 的本机启动状态源。
  2. 如果 workstate.json 缺失或没有可信 author，先让用户确认 author，再用 generate-workstate 写入。
  3. 创建新 worktree 时，create-project-worktree 会按显式 --author、已有 workstate.json.author、Git credential、远程 URL username 的顺序尝试解析；仍无法唯一确认时要求显式传入 --author。
  4. 确认后写入新 worktree 根目录 workstate.json，不要额外创建隐藏状态目录。
  5. 用 {author} 创建或读取 项目大脑/用户/{author}/。
已存在仓库里，git user.name 和 git user.email 只用于辅助识别历史别名，不能单独决定用户目录。新建任务 worktree 时，create-project-worktree 会把 Git identity、workstate.json.author、workstate.json.git_user_name 和用户目录 author 锚定为同一个远端账号。

workstate.json 规则

workstate.json 是仓库根目录下的本机冷启动状态文件，不入库。冷启动时 task_folder 默认是空字符串；等用户明确当前要做什么以后，再创建具体任务子文件夹，并更新 workstate.json.task_folder。

{
  "author": "{author}",
  "task_folder": "",
  "git_user_name": "{author}",
  "git_user_email": "{author}@kingsoft.com",
  "remote": "origin",
  "source": "manual-confirmed",
  "updated_at": "YYYY-MM-DDT00:00:00+08:00"
}
  • author 必须是当前操作者的远程账号或用户明确确认的稳定身份。
  • 冷启动时，task_folder 为空字符串，表示当前 worktree 尚未绑定具体任务。
  • 明确任务后，创建 项目大脑/用户/{author}/tasks/{task-id}/，再把 task_folder 更新为具体任务子文件夹。
  • 非空 task_folder 必须位于 项目大脑/用户/{author}/ 下。
  • 脚本写出使用 UTF-8；读取时接受 UTF-8 BOM，避免外部工具生成的 JSON 让冷启动失败。
  • 如果文件缺失、路径不存在、author 和路径不一致，agent 必须停止并询问用户。

Git 与 worktree 规则

  • 当前分支更新默认使用 git fetch + git rebase origin/<target-branch>。
  • rebase 冲突时，在 rebase 流程内逐文件解决，执行 git add 后继续 git rebase --continue，不要转成 merge。
  • 把 main 更新进当前分支时，默认 git fetch origin main 后 rebase 到 origin/main；只有明确需要保留合并关系时才显式 merge。
  • 禁止直接 git pull，避免跳过差异审查和整合方式选择。
  • 准备推送当前分支或 main 时读取 项目大脑/skills/perfect-push/；提交和验收后运行预检，确认 origin/main 是当前 HEAD 的祖先，并审查将进入 main 的提交和 diff stat。
  • Agent 不允许直接 push 到 main；push main 必须二次确认。
  • 项目大脑/启动.md、项目大脑/主流程.md 和 项目大脑/index.md 是 leader 收口文件，只允许 tech-lead 修改；其他 author 需要调整时，先在当前任务 process.md 记录建议。
  • 项目大脑/主规则.md 是受保护入口文件，Agent 修改前必须获得用户二次确认。

skill: 项目大脑/skills/generate-workstate/

  • --task-folder 可省略；省略时写入空字符串。

  • fork-project-task 是低频分支 skill；用于继承旧任务上下文但开启新目标。
