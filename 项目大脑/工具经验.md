# 工具经验

本文记录跨任务复用的系统工具使用经验，用来提高 agent 执行命令、处理文件和运行开发命令的成功率。

本文的“工具”指系统工具和通用开发工具，例如 PowerShell、cmd/bat、Git、Python/uv、Node/npm、文件编码和行尾处理。项目自己实现的工具、项目业务功能、项目内部调试器、项目内 launcher、MCP 业务动作、项目业务问题定位、业务功能验收等，不写入本文；它们应写入对应项目文档、任务 `process.md` 或模块说明。

## 使用规则

- 遇到系统命令行、脚本、文件编码、依赖管理、构建命令、Git diff 等工具问题时，先查看本文是否已有对应经验。
- 新增经验必须同时满足：
  - 高价值：一旦踩坑会浪费明显时间，或会导致误判、误提交、重复返工。
  - 高频或高复现：已经跨任务重复出现，或在本项目日常工作流里很容易再次出现。
  - 有有效解法：必须有验证过的优先做法和验证方式，不只记录现象。
  - 可复用：能指导后续 agent 在类似场景一次做对。
- 低频一次性配置、项目内工具用法、项目业务调试流程、项目业务问题定位、业务功能验收、只适用于某次任务的尝试、没有稳定解决方案的问题，不写入本文；写入当前任务 `process.md` 或对应项目文档即可。
- 新增经验必须来自真实踩坑、明确验证或用户确认，不写泛泛建议。
- 每条经验按固定结构写：`场景`、`症状`、`优先做法`、`避免做法`、`验证方式`。
- 本文只记录可跨任务复用的工具方法；单个任务的过程和临时尝试写入当前任务 `process.md`。

## YYYY-MM-DD: PowerShell 编码和中文路径处理

### 场景

在 Windows PowerShell 中读取、写入、管道传输或传给 Python/Node 命令的内容包含中文路径、中文文件名、中文正文或 UTF-8 文件。

### 症状

- 中文路径在 Python 中变成 `????` 或找不到文件。
- `python -c` 中的中文路径、换行和反斜杠转义互相干扰。
- `Get-Content`、`Set-Content`、`Out-File` 或重定向后文件编码变化。
- 管道传输中文内容后，脚本收到的文本和原文件不一致。
- 控制台能显示，但脚本读取结果乱码，说明显示编码和进程输入编码不一致。

### 优先做法

1. 读文件时显式使用 UTF-8。

```powershell
Get-Content -LiteralPath "项目大脑\说明.html" -Encoding UTF8
```

2. Python 读写文件时显式指定编码；读取外部工具生成的 JSON/文本时优先接受 UTF-8 BOM。

```python
text = path.read_text(encoding="utf-8-sig")
path.write_text(text, encoding="utf-8")
```

3. 需要在 PowerShell 中调用 Python 处理中文路径时，优先使用 here-string，把复杂逻辑放到 Python 脚本体里；路径用 `chr()` 组装，避免 PowerShell 先破坏中文。

```powershell
@'
from pathlib import Path

project = ''.join(map(chr, [0x9879, 0x76ee, 0x4fe1, 0x606f, 0x5de5, 0x7a0b]))
html = ''.join(map(chr, [0x8bf4, 0x660e])) + ".html"
path = Path(project) / html
print(path.exists())
'@ | python -
```

4. 当前会话需要大量中文输出时，先设置 PowerShell 输出编码。

```powershell
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()
$OutputEncoding = [System.Text.UTF8Encoding]::new()
chcp 65001
```

5. 编辑仓库文件时优先使用 `apply_patch`，避免 `Set-Content` / `Out-File` 改变已有文件编码。

6. 传文件路径给 PowerShell cmdlet 时优先使用 `-LiteralPath`，避免方括号、通配符或转义影响路径解析。

```powershell
Get-Content -LiteralPath "项目大脑\初始分工表.md" -Encoding UTF8
```

### 避免做法

- 避免在 `python -c "..."` 中直接拼中文路径和多行逻辑。
- 避免通过 PowerShell 管道把复杂中文正文传给 Python/Node 后再写回文件。
- 避免省略 `-Encoding UTF8` 后使用 `Set-Content`、`Out-File` 或 `>` 重定向写 Markdown/HTML/JSON。
- 避免用显示正常来判断文件编码正常；必须让目标程序实际读取验证。

### 验证方式

- HTML 文件用 Python `HTMLParser` 实际读取解析。
- Python 脚本用 `python -m py_compile`。
- Markdown/JSON/脚本改动后跑 `git diff --check`。
- 涉及中文路径时，用脚本实际 `Path.exists()` 或读取目标文件，不只看命令行显示。

## YYYY-MM-DD: Windows BAT 和中文路径

### 场景

维护 Windows 批处理入口，且仓库、工作目录或参数里带中文路径。

### 症状

- 双击或 `cmd /c` 后出现中文乱码。
- 控制台报 `'xxx' 不是内部或外部命令`，但源码看起来只是普通 echo 或路径。
- Python/API 测试通过，真实 `.bat` 入口却无法启动。
- `npm ci` 在 Windows 上重建 `node_modules` 时因原生文件被占用报 `EPERM unlink`。

### 优先做法

1. BAT 源码尽量保持 ASCII；必须显示中文时优先让 Python/GUI 输出，不把复杂中文写进 BAT 控制流。
2. BAT 放到目标目录附近，用 `%~dp0` 推导根目录，少写中文绝对路径。

```bat
@echo off
set "ROOT=%~dp0"
pushd "%ROOT%"
```

3. 修改 BAT 后必须用真实入口验证。

```powershell
cmd /d /c start.bat --help
```

4. 脚本依赖如果能随仓库固定版本，就不要让入口依赖用户全局安装或不稳定在线服务。
5. 必须从 Python 调 Node 命令时，在 Windows 上用 `shutil.which("npx.cmd")` / `shutil.which("npm.cmd")` 找 `.cmd` 包装脚本。
6. 对已有 `node_modules` 的项目，优先 `npm install`；只有确认没有进程占用、且允许删除重建依赖时才用 `npm ci`。

### 避免做法

- 避免在 BAT 里硬编码中文绝对路径。
- 避免只跑 Python 函数或 HTTP API，就认为双击入口可用。
- 避免在 Windows 正有服务占用前端原生包时直接 `npm ci`。

### 验证方式

- `cmd /d /c start.bat --help` 或真实启动命令能正常退出/启动。
- `python -m py_compile` 检查被 BAT 调用的 Python 入口。
- 临时移除或隔离 `node_modules` 后验证脚本的依赖检查是否给出清楚错误。

## YYYY-MM-DD: Node/npm 构建产物和静态资源

### 场景

用 Node/npm/Vite 构建或服务前端静态资源，尤其是 fresh pull、切分支、资源迁移、音频/图片新增之后。

### 症状

- `dist/index.html` 指向的真实 JS bundle 不存在。
- `dist/index.html` 引用了一个不存在的 `/assets/index-*.js`。
- 构建产物里缺少静态资源目录。

### 优先做法

1. 不信任仓库里的旧 `dist/index.html`；`dist/` 通常被 `.gitignore` 忽略，bundle 需要本地重新生成。
2. 有 `node_modules` 时，服务 `dist` 前先跑前端构建。

```powershell
cd client
npm run build
```

3. 没有 `node_modules` 时先安装依赖，再构建。
4. 新增静态资源后，检查构建产物中资源文件是否存在，静态服务访问是否返回 200 和正确 Content-Type。

### 避免做法

- 避免把“HTML 200”当成构建产物完整。
- 避免手工修改 `dist/index.html` 追构建产物问题。
- 避免只在 dev server 检查资源，忽略生产静态服务路径。

### 验证方式

- `npm run build` 通过。
- 用构建后的静态服务或文件清单确认 bundle 和关键资源存在。

## YYYY-MM-DD: Python 依赖、uv 环境和模块路径

### 场景

直接运行 Python 服务、测试或脚本，特别是绕过项目推荐入口手动启动时。

### 症状

- 系统 Python 缺 `py_trees`、`pytest`、`pgvector`、`openai` 等依赖。
- 手动启动时报生成代码包或本地包找不到。
- 同一个测试在系统 Python 和项目 uv 环境结果不同。
- 纯函数测试为了导入顶层路由而加载数据库/外部依赖。

### 优先做法

1. 优先使用项目推荐的 Python/uv 入口，不随手混用系统 Python。
2. 子目录有自己的 `pyproject.toml` 时，在对应目录用 `uv sync --locked` 验证锁文件。
3. 临时跑只需要 pytest 的测试时，可用 `uv run --with pytest ...`，不要把 pytest 塞进运行依赖。
4. 手动绕过推荐入口启动时，确认生成代码目录或本地包路径在 `PYTHONPATH`。
5. 纯函数单测不要因为导入顶层路由而加载数据库、模型服务和外部网络；必要时把重依赖隔离或 stub。

### 避免做法

- 避免混用系统 Python 结果和 uv 环境结果做结论。
- 避免为了让测试跑通，把开发测试依赖加入生产依赖。
- 避免手动启动失败后立刻改业务代码；先确认环境路径。

### 验证方式

- `uv sync --locked` 通过。
- 目标测试在预期 uv 环境通过。
- `python -m py_compile` / `python -m compileall` 通过。
- 手动启动的服务关闭后无端口监听残留。

## YYYY-MM-DD: Windows 行尾、BOM 和 diff 噪声

### 场景

在 Windows 上用 patch、格式化工具、PowerShell、Python 脚本修改已有源码和文档。

### 症状

- `git diff` 显示整文件改动，但逻辑只改了几行。
- `git diff --check` 报大量行尾空白，其实是 CRLF/LF 混用造成。
- `git diff --cached --check` 在提交前报 `trailing whitespace`，但工作区普通读取看不出行尾有空格。
- 新增 Markdown 只在少数行出现 CRLF，表现为 staged diff 每行末尾有隐藏的 `\r`。
- 文件原本有 UTF-8 BOM，被机械读写去掉后出现无关 diff。

### 优先做法

1. 修改后用 `git diff --stat` 和 `git diff --check` 看是否有行尾噪声。
2. 用 `git ls-files --eol <path>` 看 index 和工作区期望行尾。
3. 只对自己改过的文件做机械行尾修正，不碰无关文件。
4. 提交前也跑 staged 检查。

```powershell
git diff --cached --check
```

5. 需要检查某个文件是否混入 CRLF / CR / BOM 时，用 Python 读字节，不靠编辑器显示判断。

```powershell
@'
from pathlib import Path

path = Path("项目大脑/用户/tech-lead/tasks/YYYY-MM-DD-project-info-harness-md-flow/process.md")
data = path.read_bytes()
print("CRLF", data.count(b"\r\n"), "CR", data.count(b"\r"), "LF", data.count(b"\n"), "BOM", data.startswith(b"\xef\xbb\xbf"))
'@ | python -
```

6. 只修自己要提交的文本文件时，把 CRLF/CR 统一为 LF，并用 UTF-8 无 BOM 写回。

```powershell
@'
from pathlib import Path

for name in [
    "项目大脑/用户/tech-lead/tasks/YYYY-MM-DD-project-info-harness-md-flow/process.md",
    "项目大脑/用户/tech-lead/tasks/YYYY-MM-DD-project-info-harness-md-flow/design.md",
]:
    path = Path(name)
    text = path.read_text(encoding="utf-8-sig")
    path.write_text(text.replace("\r\n", "\n").replace("\r", "\n"), encoding="utf-8", newline="\n")
'@ | python -
```

7. 文件原本带 BOM 时，除非明确要改编码，否则保持原编码形态；如果要统一为 UTF-8 无 BOM，需要让这次提交明确包含编码治理。

### 避免做法

- 避免为了压 warning，把整批仓库文件统一换行。
- 避免把行尾修正和逻辑修改混在一个不可读 diff 里。
- 避免把工具造成的 BOM/行尾变化当成有意义改动提交。

### 验证方式

- `git diff --stat` 与实际改动规模匹配。
- `git diff --check` 通过。
- `git diff --cached --check` 通过。
- `git diff --word-diff` 或普通 diff 能看清真实逻辑改动。

## YYYY-MM-DD: 远程手机审阅 HTML 和报告文件

### 场景

用户通过手机远程查看工作结果，或者明确说看不到内网、本机浏览器、`127.0.0.1`、`localhost`、artifact 预览链接。

### 症状

- 本机静态服务或内置浏览器已经打开页面，但用户远程端无法访问。
- 大型 `说明.html`、报告、流程图页面用 artifact 展示时参数和页面都很大，沟通成本高。
- 用户真正需要的是仓库里的实体文件，而不是当前机器上的临时预览链接。

### 优先做法

1. 把 HTML、报告或说明文档写回仓库内的明确文件路径。
2. 最终回复给出仓库文件路径，不把 `127.0.0.1` / `localhost` 作为主要交付。
3. 如果只是临时预览，可启动本机服务辅助自己检查；检查完要关闭临时进程。
4. 若文件已经存在，优先覆盖或更新同一份权威文件，避免复制出多份“审阅版”造成混乱。

### 避免做法

- 避免把本机内网链接当成远程用户可打开的交付物。
- 避免为了展示一份已经落盘的大 HTML，把整份文件塞进 artifact 形成额外的大副本。
- 避免同时保留多个内容接近的 HTML 版本，让用户不知道哪个是新的。

### 验证方式

- 确认目标文件真实存在，路径和更新时间正确。
- HTML 文件用解析器或浏览器检查过基础可读性。
- 临时静态服务、测试浏览器进程等辅助进程已经关闭。
