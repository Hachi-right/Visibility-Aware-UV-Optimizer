# 非技术人员操作安全护栏

> 用途: 给非程序员成员使用的强制简化操作安全护栏。
> 适用: `初始分工表.md` 中除程序员、主程序、模型专家程序和技术策划外的成员；【团队负责人·示例】按技术策划处理，不纳入本规则对象。
> 加载: 适用成员的 `私有流程.md` 必须在 `私有规则.md` 之前读取本文。
> 关联: Git 安全操作使用 `项目大脑/skills/perfect-push/`；触及核心框架时须发件给对应程序员审查后再合入。

## 最高规则

- 非技术人员及其 AI 尽量不要修改【示例-core模块】和【示例-runtime模块】的核心调度代码
- 如果 diff 触及核心模块中的状态同步、权限校验、事件分发或对外契约输入链路，视为最高风险
- 提交前须盘点改动范围；触及核心框架时不得自行合入，须发件给对应程序员审查。

## 强制 Git 规则

- 只要不是纯写文档，而是要改代码或配置，就必须先开 worktree 和分支；做新功能、优化、改 bug 都算，不要直接在 `main` 上改，避免把主干改坏或误提交。
- 用户说"提交"时，agent 须先说明改动范围、验证结果和风险；确认后再 `git commit`，不要跳过说明直接提交。
- 用户说"提交"后，涉及 `fetch`、`rebase`、冲突处理、推当前分支和推 `main` 的步骤，都按 `项目大脑/skills/perfect-push/` 执行；不要直接 `pull`。
- 不要改坏别人的代码，不要覆盖用户或其他人的修改；这是写给 agent 的操作原则，不是让非技术人员自己判断。遇到冲突、未提交改动或不确定归属时，agent 要主动分析并尽量自动解决，保留双方有效修改；不要把代码取舍问题丢给非技术人员确认。
- 用户说"更新"时，如果当前在 worktree，就沿用 `perfect-push` 的 Git 安全口径，用 `fetch` + `rebase` 从 `main` 把新内容同步过来，不要直接 `pull`。
- 用户说"收件"时，先更新 `main`，然后再收件。
- 用户说"发件"时，邮件内容必须 push 到 `main`，别人才可以收到。

## 修改边界

- 修改代码前必须查看职责边界，查阅相关文档和相关人员的工作记录，先理解对方的设计架构；要适应现有架构，不要粗暴修改架构和框架代码。
- 修改尽量保持最小范围，不要扩大到无关位置，不要顺手发散修 bug。
- 业务修改优先改配置文件、表格、回调脚本、业务函数、外挂脚本或 UI 表现；不要轻易改核心代码和框架代码。
- 如果改动已经落到了核心代码或框架代码区域，提交前须向用户说明风险，并建议发件给对应程序员审查；不直接原样合入 main。

## 核心代码和框架告警

以下改动默认视为高风险；非技术人员应了解风险，但不自行判断最终是否可合入——须由程序员审查：

| 类型 | 浅显解释 |
| --- | --- |
| 核心服务 / 调度 / 状态机 | 会影响系统怎么理解输入、做决策和执行动作。 |
| 权限 / 校验 / 同步机制 | 会影响谁能做什么、数据如何保持一致；核心模块中的这类代码属于最高规则保护范围。 |
| 事件 / 消息 / 任务分发 | 会影响各模块之间的触发、排序和响应链路。 |
| 外部接口 / 插件 / 扩展点 | 会影响系统能调用哪些能力，以及参数怎么校验。 |
| 【示例-backend模块】 权威执行 / 动作校验 | 会影响业务状态、合法性、同步、回滚和结算。 |
| 前端 / 编辑器框架层 | 会影响通用渲染、输入、编辑器生产链路或其他人的配置工作流。 |
| 协议 / 启动脚本 / 项目大脑启动与提交流程 | 会影响联调入口、跨端契约、任务留痕或团队协作规则。 |

## 提交流程（非技术人员专用）

非技术人员说"提交"时，agent 必须按以下流程执行，**不得跳过直接 commit**：

1. **盘点范围**：用功能语言向用户说明改了什么、为什么改、验证了哪些路径。
2. **风险扫描**：对照上表检查是否触及核心框架；若触及，写清风险并建议发件给程序员审查。
3. **验收**：按 `project-validation` 执行与改动匹配的最小验收。
4. **提交与推送**：用户确认后 `git commit`；说"推送"时走 `perfect-push`。
5. **不能自动判定时**：把问题记录为"决策"，写清选项和影响；发件给对应负责人请求拍板。

## 测试与问题报告

- 测试或联调发现问题时，agent 必须用浅显语言说明问题现象、影响范围、已验证证据和建议解决方案；不要只甩日志、代码文件名或专业术语给非技术人员。
- 如果遇到的 bug 确实需要修改核心代码或框架代码，须说明风险并请程序员审查后再改。
- 如果现有机制和框架可以解决，但分支代码又发明了新机制或绕过了框架，须调整实现方式以适配框架和既有接口，而不是原样合入。
