# index-tiering-methodology

本 skill 解决“索引越来越长以后如何拆成可预测结构”。它只负责方法论：怎么分、叫什么、怎么保持可查；不负责执行脚本。

## 适用对象

- 公共或私人 `index.md`。
- `经验/`、`公理/`、`代码地图/`、`资料地图/`。
- 会议资料、顶层设计、设计资料、规则资料、skill 清单、任务列表。
- 任何“入口越来越多，agent 看不出该读哪里”的列表或知识库。

## 触发条件

- 一级索引接近或超过 50 条。
- 同类条目超过 7 到 10 条，继续堆叠会难以扫描。
- 一个索引混入不同读者、场景、生命周期或写入边界。
- agent 需要二次理解路径含义，才能判断该读哪个文档。
- 多个 worktree 或多人会频繁更新同一个长清单。

少量临时条目、一次性任务过程、已有明确稳定归属的目录，不需要强行分级。

## 分级原则

1. 先按使用场景归类，再按存放位置归类；不要优先按日期、编号或临时标题分。
2. 一级索引只保留分类入口和一句话用途。
3. 二级索引列具体文档、目录或 skill，并写清“何时看它”。
4. 条目文档跟随同一分类进入子文件夹；已有稳定归属的目录不强行移动。
5. 二级索引继续膨胀时再拆三级，仍按场景、领域或读者分。
6. 分类名要稳定、短、可预测，例如 `会议资料`、`顶层设计`、`公共skills`、`私人经验`、`交付规则`、`配置与表格`。
7. 不一条一个索引，不复制正文，不跨 author 整理私人区。

## 工作流程

1. 收集条目：路径、标题、用途、触发场景、读者、生命周期、写入边界。
2. 合并同义：去掉近义分类，保留最通用、最可预测的命名。
3. 画目标树：一级分类 -> 二级索引 -> 具体条目。
4. 迁移索引：一级只指向分类，二级保存具体条目。
5. 校验反查：用 3 个真实任务场景从场景反查到条目，确认不需要全局扫描。
6. 写回任务：过程写当前任务 `process.md`，稳定设计决策写 `design.md`。

## 输出格式

一级索引只放分类入口：

```markdown
| `索引/会议资料.md` | 会议资料二级索引；遇到会议纪要、录音转写、会议共识时看。 |
```

二级索引保存具体入口：

```markdown
# 会议资料索引

> 用途: 会议转写、会议纪要和会议共识的二级索引。

| 文档 | 何时查看 |
| --- | --- |
| `../../docs/meeting/YYYY-MM-DD_主题.md` | 遇到某主题协作边界、会议结论或历史共识时查看。 |
```

## 和 project-index-maintenance 的关系

- 本 skill 负责通用分级方法，适用于所有增长型索引和知识库。
- `project-index-maintenance` 负责公共/私人 `index.md` 的脚本化检查、自动拆分和健康验证。
- 自动拆分后分类不理想时，先用本 skill 复核分类，再人工整理。
