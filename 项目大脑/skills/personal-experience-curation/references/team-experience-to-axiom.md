# 团队经验 → 团队规则（上升路径）

> 用途: 把**多源验证过的项目不变量/硬规则**写入 `docs/规则/` 对应分册。
> **维护权限**: 仅 `team-lead`、`tech-lead` 可整理/写入/修改 `docs/规则/` 协作与设计类分册；代码类分册随规范 task 维护。其他 author **禁止**直接改，只可提名。
> 默认披露: **规则层 + 资料地图层 + 索引层**；不默认改 `主流程.md` / `主规则.md`。
> **废止**: 原 `项目大脑/公理/` **P 系列规则正文**已迁入 `docs/规则/`（YYYY-MM-DD）。`公理/` 已复兴为**团队公理思考层**（见 `项目大脑/公理/index.md`）；本文件写入目标仍为 `docs/规则/` **不变量**。

## 三层认知分工（必读）

| 层 | 路径 | 回答 | 形态 | 谁维护 | 典型读者 |
| --- | --- | --- | --- | --- | --- |
| **团队经验** | `团队经验/entries/` | 在什么争论里、为何这个判断有效 | 反常点 + 边界 + 反例 + 情境 | 会议/task 蒸馏；双写规则 | 任务开始时点读 1–3 篇 |
| **团队公理** | `公理/entries/` | 多条经验**抽象**后的项目内**为什么** | 六段式深文；**精而不多** | team-lead 拍板升维 | 战略/架构/agent 推导 |
| **团队规则** | `docs/规则/{主题}.md` | 做某类事时**必须遵守的不变量/拆解语法/硬约束** | 主题聚类表 | **仅 team-lead / tech-lead**（协作/设计）；代码分册随规范维护 | 设计/实现/协作拿不准时按需 |
| **个人公理** | `用户/team-lead/skills/personal-axioms/` | 主创**为什么**这样看（世界观/管理哲学） | 长文：深度推演 + 应用判定 | 仅 team-lead | advisor-lens、战略取舍 |

**硬边界**

- 团队规则 **≠** 去情境化的经验摘要。若去掉 task 名后只剩「我们倾向于…」，仍应留在团队经验。
- 团队规则 **≠** 个人公理公共化。含价值观、管理哲学、个人效率观 → 留 `personal-axioms`；advisor-lens 引用，不进 `docs/规则/`。
- 团队规则 **=** 本项目可共享的**工程/设计/协作不变量**（类似 P10–P16：状态归属、原子正交、统一执行流水线）。

## 维护权限

| 动作 | team-lead | tech-lead | 其他 author |
| --- | --- | --- | --- |
| 写入/修改 `docs/规则/`（协作/设计分册） | ✓ | ✓ | ✗ |
| 从团队经验发起上升 | ✓ 拍板 + 可自落盘 | ✓ 落盘 + leader整理确认 | ✗ 仅可 **提名** |
| 提名方式 | — | — | 写本人 task `process.md` 或 team-lead **收件**；不得改 `docs/规则/` |

agent 遇到非 team-lead/tech-lead author 要求「写进团队规则/公理」：只记录提名到 task/收件，**不**改 `docs/规则/`。

## 公理资格测试（须全部通过）

从团队经验上升前，候选须通过 **AQT**；任一条不通过 → **留在团队经验**，只可加 `公理候选: 暂缓/{原因}`。

| # | 测试 | 通过标准 | 不通过信号 |
| --- | --- | --- | --- |
| A1 | **不变量** | 能写成「做 X 时，必须/禁止 Y」或固定拆解问句（状态归谁？原子是什么？执行收束到哪？） | 只能是「我们倾向于」「在某次讨论中认识到」 |
| A2 | **多源** | ≥2 个独立来源：不同 task、不同会议、或 team entry + `docs/` 设计文档、或 ≥2 位 author 实践验证 | 仅 1 条 team entry、单次口述 |
| A3 | **非个人哲学** | 任何 IC 不看主创世界观也能执行；不依赖 A/T/M/V/X 个人公理才能懂 | 正文引用 A03/V01 等作为**唯一**依据 |
| A4 | **高于经验** | 教**如何结构化方案**，不是**某次争议结论** | 与 team entry 认知字段同义换写 |
| A5 | **可验收** | 能列出 2–3 个 yes/no 检查问句 | 只能「读一下体会」 |
| A6 | **边界已沉淀** | 反例/张力已在 team entry **边界**字段吸收；公理只写默认模式 | INDEX「已知张力」未分层 |

**频率门槛**: 团队经验被 **≥2 次** 不同来源强化，只是 A2 的必要条件之一，**不自动上升**。

## 触发时机

| 触发 | 谁执行 |
| --- | --- |
| team-lead / tech-lead 说「上升公理」「整理团队公理」 | team-lead 或 tech-lead |
| `leader-public-curation` 扫描公理候选 | tech-lead（仅 tech-lead 可跑） |
| 其他 author 认为某条应上升 | 提名 → team-lead 或 tech-lead 评估 |

**不触发**: 单条经验首次写入、AQT 未全过、与个人公理同域、与现有 Pxx 同义。

## 执行流程（仅 team-lead / tech-lead）

```
1. 读 `docs/规则/index.md` 场景表 + 目标主题分册现有 Pxx
2. 读候选 团队经验/entries/（可多篇）+ 关联 docs/design/task 证据
3. 跑 AQT 六条 → 全过才继续；否则写暂缓原因
4. 合成不变量（见「合成规则」）→ 归并已有 Pxx 或新增行
5. 回写 team entry：`公理支撑: Pxx` 或 `公理候选: 暂缓/{原因}`（禁止只升不写回）
6. 可选：资料地图关键词路由（不改主流程）
7. tech-lead → leader整理确认.md；team-lead 直落盘 → task process.md
8. healthcheck
```

## 合成规则（拉开与经验的差距）

**禁止**: 把 team entry 的「认知」「为何有效」删几个字贴进公理表。

**必须**: 从一条或多条经验**抽象出**本项目专属的不变量或拆解语法：

| 经验类型 | 公理合成方向 | 示例 |
| --- | --- | --- |
| 争议型（B/C 类） | 提炼**决策检查问句**或**架构约束** | C1 索引≠必读 → 强化 P06 + 新增检查问句：「该内容命中率是否足以进冷启动？」 |
| 设计型（D 类 + docs） | 提炼**状态/流水线/分层不变量** | D1 + 设计 docs → P12 类「LLM 选、规则算」不变量 |
| 协作型 | 提炼**写入边界/隔离/披露层级** | 已有 P05–P09 域内归并 |

公理表「公理」列：写**不变量短句**；「核心含义」列：写**拆解/检查方法**；「何时使用」列：写**工程场景触发词**（不含 task/会议名）。

## 字段映射

| 来源 | 公理表列 | 要点 |
| --- | --- | --- |
| 多条 team entry + docs 验证 | 公理 + 核心含义 | 合成不变量，非单条摘要 |
| 工程触发场景 | 何时使用 | 模块/活动类型关键词 |
| team entries + task/design | 来源 | 列主要 entry 路径；多源必填 |
| — | 状态 | 新条 `初版`；跨 task 验证后 `稳定` |

## 写入位置

| 域 | 文件 |
| --- | --- |

## 与个人公理、advisor-lens 的关系

```
团队经验 ──(AQT + 多源 + 仅 team-lead/tech-lead)──► 团队规则（docs/规则/）
                                                      │
个人公理 ◄── advisor-lens 并行引用，不写入 ──────────┘
（主创为什么）
```

- B0 引 T02/A03：team entry 可保留公理引用；**上升**时须 AQT-A3——若去掉个人公理即无法成立，**不上升**。
- advisor-lens：team 公理（不变量）+ personal 公理（为什么）+ team 经验（情境）；三层分轨输出。

- [ ] team entry 已回写 `公理支撑` 或 `公理候选: 暂缓`
