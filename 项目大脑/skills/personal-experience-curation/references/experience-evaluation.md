# 经验评判机制

## 核心原则

经验不是任务流水。只有能让后续任务更快判断、更少搜索、更少返工、更少跑偏，且具备前因后果和证据的信息，才进入私人经验库或公共候选。

每个候选在写入前必须回答六个问题：

| 问题 | 要求 |
| --- | --- |
| 来源是什么 | 指向任务 `process.md`、`design.md`、`任务范围.md`、`任务指标.md`、会议文档、代码地图差异或用户原话。 |
| 前因是什么 | 写清为什么会发生、为什么会错、为什么返工、为什么重要。 |
| 结论是什么 | 写清最终确认的新知识、规则、方法、边界或教训。 |
| 下次如何用 | 写清遇到什么场景读它、用它做什么、如何避免旧错误。 |
| 证据是什么 | 用户确认、验收结果、多次复现、代码/文档验证、设计决策或明确失败归因。 |
| 复用范围是什么 | 当前 author 私人、跨任务候选、跨成员公共候选，或只保留在原任务。 |

缺少前因后果的内容不要直接沉淀。能补证据就先补；不能补就保留在当前任务记录，不提升成经验。

## 评分表

每个候选按 0-2 分评分，总分 10 分。

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 复用价值 | 只对当前一步有用 | 同类任务可能有用 | 能明显减少后续搜索、返工或误判 |
| 证据强度 | 只是猜测 | 有单次验证或用户倾向 | 有用户确认、验收、复现或稳定设计决策 |
| 上下文完整 | 只有结论 | 有部分前因或适用场景 | 有来源、前因、结论、适用场景和限制 |
| 稳定性 | 很快会过期 | 依赖当前阶段但短期可用 | 项目/团队/工具层面相对稳定 |
| 可检索可行动 | 标题和摘要模糊 | 能找到但下次动作不清 | 可通过场景关键词命中，并直接指导下一步 |

判定：

| 分数 | 处理 |
| --- | --- |
| 7-10 | 写入主题经验文档，或作为 leader 公共抽取候选。 |
| 4-6 | 只在私人 `index.md` 或资料/代码地图里索引原始文件；摘要必须写前因、结论和何时读取。证据不足时留在当前任务 `process.md`。 |
| 0-3 | 丢弃，不进入经验库。 |

## 硬拒绝

出现任一情况时，不写入经验文档：

- 没有来源路径或无法说明来源。
- 没有前因后果，只有“做了什么”的流水。
- 未验证猜测、临时 workaround、一次性命令输出、环境瞬态状态。
- 已被现有经验覆盖，且没有新增场景、证据或限制。
- 包含密钥、token、cookie、账号隐私或不应入库的敏感信息。
- 涉及其他 author 私人区写入，且没有该 author 或用户明确授权。
- 想提升为公共规则，但还没有跨任务或跨成员证据。

## 写成总结文档

满足以下至少一项，且评分不低于 7 分时，写入 `项目大脑/用户/{author}/经验/{主题}.md`：

- 改变后续工作流、验收方式、任务拆解、文档入库、调试路径或协作边界。
- 记录稳定项目知识、重要设计决策、被推翻旧口径或常犯错误。
- 能作为测试方法、环境搭建方法、需求梳理方法、写文档方法、调试方法、需求拆解方法、checklist 或模板。
- 能帮助下次更快找到代码、资料、配置、脚本、表格、资源、会议或设计文档。

总结文档必须写清触发、前因、结论、下次做法、不要做、适用场景、来源和状态。

## 只做索引

以下情况优先只写索引，不另写总结文档：

- 原始文档本身已经完整表达背景、结论和细节，后续主要需要“知道去哪里看”。
- 经验本质是资料入口、代码入口、会议入口或设计文档入口。
- 候选有价值但证据不足，暂时只需要在私人索引或当前任务里标注。

索引摘要必须包含：

```markdown
| `路径` | 遇到{场景}时查看；前因: {为什么产生这条记录}; 结论: {下次要怎么做或去哪里看}; 来源: `{原始路径}`。 |
```

不要在索引里复制正文。

## 丢弃与保留在任务内

以下内容只保留在当前任务 `process.md`、`任务指标.md` 或原始日志里：

- 阶段状态、命令输出、一次性验收流水。
- 没有复用价值的失败尝试。
- 只说明“通过/失败”，但没有失败归因、修正方法或可复用边界。
- 短期分支状态、临时路径、临时端口、临时截图。

丢弃不是删除历史；它只是表示不提升到经验库，避免后续检索时被无用信息干扰。
