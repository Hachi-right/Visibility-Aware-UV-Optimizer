# 经验整理收录标准

本标准用于私人经验整理和 leader 公共抽取。它借鉴预制菜绿色版的分层记忆、公理索引、信息密度、闭环校准和上下文隔离做法，但不直接照搬其目录。

## 核心判断

一条候选信息只有同时满足以下条件，才值得进入经验、公理、代码地图或资料地图：

| 判断项 | 通过标准 |
| --- | --- |
| 长期价值 | 未来 3 个月内可能复用，能减少搜索、返工、跑偏或冲突。 |
| 证据闭环 | 有用户确认、验收结果、复现记录、失败归因、代码/文档验证或稳定设计决策。 |
| 前因后果 | 写得清为什么出现、为什么重要、最终结论是什么、下次怎么用。 |
| 检索命中 | 能用场景关键词、模块名、人名、文件类型、功能名或错误特征找到。 |
| 行动价值 | 读完能指导下一步动作，而不是只知道曾经发生过。 |

缺任何一项时，不直接提升。能补证据就先补；补不了就留在当前任务 `process.md`。

## 分层口径

| 层级 | 写入位置 | 用途 |
| --- | --- | --- |
| L0 任务过程 | 当前任务 `process.md`、`任务指标.md` | 保存当次过程、日志、失败尝试和临时状态。 |
| L1 私人经验 | `项目大脑/用户/{author}/经验/`、私人 `代码地图/`、私人 `资料地图/` | 当前 author 下次可复用的经验、方法、查找入口和差异。 |
| L2 公共抽取 | 公共 `docs/规则/`（协作/设计分册）、`代码地图/`、`资料地图/`、必要公共 skill | leader 从多人/多任务验证过的内容中抽取团队共识。 |
| L3 硬规则 | `主规则.md`、`docs/规则/index.md`、模块 `CONSTRAINTS.md` | 必须长期遵守的规则，修改前需更高确认。 |

不要从 L0 直接跳到 L2/L3，除非用户明确指定或证据足够强。

## 收录

优先收录以下内容：

- 用户明确说“下次要/不要”“记住”“以后这样处理”，且上下文清楚。
- 多轮纠错后形成的稳定结论，尤其是之前反复踩坑的问题。
- 改变验收流程、测试方法、启动方法、文档入库、调试路径、职责边界或协作方式的经验。
- 能显著提高代码、配置、文档、资源、会议记录或设计资料查找命中率的入口。
- 代码地图或资料地图中被多次使用、被验证有效、或公共地图缺失的查找路径。
- 已被成员私人区验证，且跨成员、跨任务可复用的团队级共识。

## 丢弃

以下内容不要提升：

- 只有“做了什么”，没有为什么和下次怎么用的流水。
- 一次性命令输出、临时端口、临时截图、短期分支状态。
- 未验证猜测、为了绕过当前问题的临时 workaround。
- 已被现有经验覆盖，且没有新增场景、证据或限制。
- 与未来任务无关的情绪、寒暄、低价值状态同步。
- 会污染检索的重复条目、同义改写和没有入口关键词的长摘要。

## 写入策略

| 场景 | 做法 |
| --- | --- |
| 原始文档完整且后续只需要找到它 | 只写索引摘要，指向原文。 |
| 候选是稳定方法或教训 | 写入已有主题经验文档；没有合适主题才新建主题。 |
| 候选是代码入口或搜索路径 | 写入当前 author 私人代码地图；公共缺失写差异列表。 |
| 候选是资料入口或搜索路径 | 写入当前 author 私人资料地图；公共缺失写差异列表。 |
| 候选跨成员可复用 | 先进入 leader 公共抽取候选，由 `tech-lead` 核实后公共化。 |
| 候选是公共共识或设计思想 | 优先写 `docs/规则/`、`资料地图/` 和必要公共索引；不默认修改 `主流程.md`。 |
| 候选会改变启动/加载流程 | 先写入当前任务 `design.md`、求证文档或待确认项；只有用户明确要求并确认影响后才修改 `主流程.md` 或 `启动.md`。 |
| 候选是硬规则 | 先记录依据和风险，不作为整理副作用修改；修改 `主规则.md` 或规范前需用户二次确认。 |

经验、代码地图、资料地图、公理都按主题聚类，不一条经验一个文件。

索引披露优先于流程披露。整理、总结和上升共识默认只让内容可被查到、按需读到；不要为了“以后能看到”就把候选塞进启动链路或条件加载流程。

## 整理前加载

整理前先加载已有整理经验，再开始判断候选，避免每次从零摸索。

- 先查当前 author 私人 `index.md`，读取和“整理经验、经验沉淀、项目大脑、文档结构、可读性、模块理解方法”相关的私人经验主题。
- 再查 `docs/规则/index.md` 和相关公共主题，读取团队已经形成共识的整理原则。
- 只读取和本次整理目标相关的主题，不全量加载私人 `经验/` 或 `docs/规则/` 全部分册。
- 如果私人经验和公共共识冲突，先按公共硬规则和用户当次要求执行，并把冲突写入求证文档。

## 整理后求证文档

整理功能早期不默认相信自己的判断。每次私人整理或 leader 公共抽取完成后，都必须额外输出一份求证文档，请使用者核对整理是否正确。

| 场景 | 求证文档位置 | 使用者 |
| --- | --- | --- |
| 私人整理 | `项目大脑/用户/{author}/经验/整理确认.md` | 当前 author |
| leader 公共抽取 | `项目大脑/用户/tech-lead/经验/leader整理确认.md` | `tech-lead` |

求证文档只写重点，不写整理流水。必须包含：

- `整理范围`: 本次读取了哪些任务、经验、代码地图、资料地图或公共候选。
- `整理依据`: 本次实际使用了哪些收录原则、丢弃原则和分层原则。
- `高把握整理点`: 只列清单，写清整理到哪里，不展开长解释。
- `低把握/待确认点`: 必须标出不确定原因、依据缺口、需要使用者确认什么。
- `未收录/暂缓项`: 简述丢弃或暂缓原因，避免下次重复判断。
- `向使用者学习`: 重点请使用者校准重要/不重要的区分标准、应该更关注的点、整理措辞、文档结构、让人类快速看懂的技巧、以及对相关模块的正确理解方法。
- `整理经验`: 如果本次学到新的整理判断方法，先写入当前 author 私人 `经验/`，并在求证文档列出写入位置。
- `用户确认`: 预留后续记录使用者确认、纠正或要求回滚的结果。

有把握的内容只列清单；不确定的内容要显眼，并说明为什么不确定。使用者纠正整理方法后，先把这条整理经验沉淀到当前 author 私人经验里，不直接公共化。

## 输出格式要求

每条沉淀至少包含：

- `触发`: 来自哪个任务、会议、用户原话或验证结果。
- `前因`: 为什么产生这条经验，旧做法哪里容易错。
- `结论`: 最终确认的规则、方法、入口或边界。
- `下次用法`: 遇到什么场景读取，读取后怎么行动。
- `证据`: 验收、用户确认、复现、代码/文档验证或公共抽取依据。
- `限制`: 适用范围、过期条件、可能冲突的旧记录。

没有这些字段时，只保留在任务过程，不提升。
