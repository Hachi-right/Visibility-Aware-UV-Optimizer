# 私人经验认知剪裁规则



> author: `team-lead`

> 用途: `personal-experience-curation` skill 的剪裁与反推标准。

> 来源: `tasks/YYYY-MM-DD-personal-experience-curation/` 当前 author多轮校准（YYYY-MM-DD）。



## 1. 写什么 / 不写什么



| 要 | 不要 |

| --- | --- |

| 抽象**经验认知**：怎么判断、为何这样判断 | 具体操作步骤、命令、改哪个文件 |

| **反常点**：不太常见但非常有效的判断 | 与 agent 内置常识接近的条目 |

| **反推**：为何有效（机制） | 只有「然后怎么做」的 SOP |

| **何时用到**：何情境认识到并用到 | 只有 task 路径的 `来源` |

| 个人认知可标注「不普适」 | 冒充团队共识或策划内共识 |



## 2. 反常点测试（每条必过）



写条目前自问：



1. **常识测试**：这条是否接近通用管理/工程常识？是 → 砍或只留索引指向原文。

2. **共识测试**：团队/策划内是否已默认认同？是 → 砍（例：涌现玩家/开发者分层）。

3. **行为测试**：删掉「执行意图」后还剩判断价值吗？否 → 重写或砍。

4. **反推测试**：能写清「为何有效」吗？只能写步骤 → 砍或问当前 author。

5. **证据测试**：有 task design/当前 author确认/实机教训吗？无 → 留 task，不进经验。

6. **反例测试**：主动找过反例吗？找到的反例能被「边界」吸收 → 条文更精确；完全找不到 → 太泛或证据不足，砍或留 task（详见 `distillation-methodology.md` §5）。



拿不准时 **问当前 author**，不要猜。



## 3. 素材优先级



| 优先级 | 素材 | 原因 |

| --- | --- | --- |

| 1 | `tasks/*/design.md` | 稳定决策，噪音少 |

| 2 | 当前 author当次口述校准 | 个人认知源头 |

| 3 | `tasks/*/process.md` | 补证据，易流水 |

| 4 | 已有 `经验/entries/*.md` | 去重、交叉引用 |
| 5 | 外部文章/演讲（`经验/references/articles/`） | 反常点原料；`entries/` 的 `来源` 填 `ref_id` |



优先扫 **已完成** task；未开始 task 不扫。



## 4. 类别聚类（对齐 axioms INDEX）



按**判断场景**分 A/B/C/D 四类，每条独立 `entries/` 文件：



| 类别 | 场景 | 范例 ID |

| --- | --- | --- |

| A 顶层设计取舍 | 双目标、节点、远期、冲刺 | A1, A2, A5, A6 |

| B 主创协作与委托 | agent 指令、委托、团队节奏 | B0, B2, B4, B6 |

| C 文档与规则架构 | 项目大脑、汇报、白皮书结构 | C1, C2, C3 |

| D 分阶段系统设计 | 模块分期、规则/配置、验收、命名 | D1, D2, D3, D4 |



新条文：在 `经验/INDEX.md` 对应类追加；单类超过 ~8 条再考虑拆子类（更新 INDEX 节标题）。

**禁止自创顶层类**：不得静默新增 E/F/… 字母类或改 A/B/C/D 边界；只允许在现有四类内追加编号，或在 INDEX 内拆子类小节。

## 4.1 author 扩展（仅 `team-lead`）

> **条件加载**：仅当 `workstate.json.author`（或用户当次明确身份）为 `team-lead` 时读本节；**其他 author 跳过，不适用**。

**某类明显装不下 → 必须停下来问当前 author**（硬闸门，优先于继续写正文）：

| 信号 | 动作 |
| --- | --- |
| 候选经验在 A/B/C/D 间**无法选定主类**，或归入任一类都会扭曲「判断场景」 | **停止**落盘 `entries/`；整理方案写清各备选归类及为何不成立 |
| 合理归档似乎需要**新顶层字母类**（非子类拆分） | **停止**；方案中提议新类名、判断场景、与现有四类的边界；等当前 author 拍板后再改 INDEX 命名规则 |
| 多条候选被**反复塞进同一错误类**，且边界字段只能写「本不属于此类」 | **停止**批量写入；先问是否扩类边界、拆子类，或新建顶层类 |

未获 `team-lead` 确认前：不得新建 `e1_...` 类文件、不得擅自改 §4 类别表、不得用「临时放 D」糊弄。

其他 author：类别体系由各自 `经验/INDEX.md` 与私人 skill 维护；本节不自动套用。



## 5. 硬删减类（首轮已验证）



| 类 | 例 | 处理 |

| --- | --- | --- |

| 架构/T05 常识 | 原则写死路线可换 | 删 |

| 策划内共识 | 涌现双域 | 删 |

| HR/敏捷 常识 | 角色标签、远期目标必填 | 删 |

| 协作红线 | 落仓对齐主程序 | 留 `职责范围.md`，不进经验认知 |

| 文档工程常识 | 单一真相源、内外版分区 | 删 |

| 防御式编程常识 | 可降级须可观察 | 删 |

| 已有具体拍板 | 道具转化数值口径 | 留 `tasks/YYYY-MM-DD-item-transform-review/道具转化验收决策.md`；`entries/` 只写抽象+交叉引用 |



剪裁记录维护在 `经验/INDEX.md` → **整理记录 → 已删减**，避免下轮重复判断。
