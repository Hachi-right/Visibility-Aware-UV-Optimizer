## L3 硬规则详情

### 任务留痕

- **任何改动仓库的工作都必须落盘可见**；不能只留在聊天、IDE 会话或 commit message。
- **唯一例外**：用户明确要求只读回答、不改仓库任何文件。
- **最低留痕**：`tasks/{task-id}/process.md`；稳定决策 `design.md`；`tasklist.md` 索引；有验收时 `任务范围.md` / `任务指标.md`。
- **改仓库前**：检查 `workstate.json.task_folder`；无活跃 task 先建（推荐 `create-project-worktree`）或挂靠已有 task。
- **main 直改不豁免**：可简化 Git 流程，但 task 流水不能省；未建则收尾补档（retroactive task）。
- **commit 不能替代 task**：`main` 提交须能在某 task `process.md` 追溯到需求、决策、验证和 commit 标识。
- 稳定结论可同步 `docs/`、`经验/`、地图，但不能只写那些位置而不写 task。

### Git

- **触发词（团队硬规则）**：用户明确说「提交到分支」时，只可 `git commit`，不可上传远端；明确说「提交到 main」「push main」「推送 main」「推送主干」或只说「推送」时，默认目标是远端 `main`，可将当前 task 范围内已验证的改动依次 `git commit` 与 `git push origin HEAD:main`。改完/验收通过 ≠ 可自动提交或推送。
- **推送须人工复核**：说明分支、commit 范围、是否合最新目标分支、验证结果；未确认前禁止推送。
- **提交是否需确认**：前述“推送到 main”用语已包含保存本次 task 改动的授权；若用户只说「提交」而未说明目标，依当前 author `工作习惯.md`、`私有规则.md` 或当次指令。
- 操作细节（fetch/rebase/冲突/预检/快进 main 证明）→ `perfect-push`；禁止直接 `git pull`。
- 不改无关文件；不清理非自己制造的改动；不覆盖他人任务状态。

### 职责与修改边界

- 改文件前读 `职责范围.md`；明显越界先拒绝并说明风险；用户坚持时确认是否修订职责范围。
- 任何 author 不得直接修改 `项目大脑/用户/{other-author}/` 私有区（写对方 `收件/` 为发件例外）。
- 交付规则确认后写入执行方 `index.md` / `职责范围.md`，并在 task `process.md` 记录来源与范围。
- 新建 skill/MCP/hook/辅助落盘默认放当前 author 私有区；稳定可复用后 leader 公共化。

### 验收与数值

- 估算、统计、占比、资源建模、公式或任何数值结论：先 `math-sense`；工具计算并记录口径、公式和验证方式。
- 验收覆盖本次改到的功能路径；核心业务链路、外部接口与业务回调须验错误日志和正常路径。
- 框架崩溃：能快修则修；不能判断则停下报告；不带已知核心错误进下一阶段。
- 改项目大脑自身时运行 `project-info-healthcheck`。
- 其他验收层级与执行顺序 → `project-validation`。

### 代码与调试（硬边界摘要）

- `docs/规则/index.md` 是入库代码规范和防御式编程规范的**场景路由入口**；分册正文在 `docs/规则/`。写代码/review 时先读 index，再点读 1–3 个分册；**禁止**全量读所有分册。`docs/规则/代码规范术语表.md` 是术语、命名和跨端统一用词补充。二者是所有 author、所有入库代码、所有 code review 和验收的最高优先级公共硬规则。
- 防御式编程细则在 `docs/规则/防御式编程.md`，验收三板斧在 `docs/规则/验收三板斧.md`（摘要见 `主流程.md` §2 R16）。人类浏览用 `项目大脑/看板/代码规范浏览.html`（非 agent 加载链）。
- 先理解模块边界再改代码；搜代码 → `project-code-map`；搜资料 → `project-search-map`。
- 新功能先查相似实现；优先复用；不为当前任务引入第二套结构。
- 外部 I/O、网络、数据库、Docker、MCP、LLM 输出、配置和业务脚本按不可靠处理；不吞错。
- 代码整改完成后必须回测对应功能无异常；仅静态检查、只改完文件或只跑无关测试，不算收口。

### 顶层设计对齐（新功能 / 新设计）

涉及**新功能、新系统设计、跨模块架构变更，或明显改变核心业务行为或对外口径**时，动手或定方案前先对照顶层设计，并向当前用户说明与愿景、技术方向的对应关系，便于团队协作。

**先读什么（按需，不必全文）**

| 层级 | 文档 | 用途 |
| --- | --- | --- |
| 愿景 | `docs/顶层设计/【示例项目】项目愿景白皮书.md` | 核心目标、产品与技术原则、路线 |
| 技术 | `docs/顶层设计/【示例项目】项目技术白皮书.md` | 技术铁律、能力栈方向、原型 vs 收敛 vs 远期 |
| 拍板 | `docs/顶层设计/【示例项目】顶层设计决策台账.md` | 已确认项与待确认项 |
| 系统 | 对应模块主创权威文档 | 数值、接口与分期细节 |

超远期理论资料仅作原则参考，不当作当前阶段的交付承诺。

**须说明什么**

用当前方案能一句话回答：满足哪些愿景 / 技术主张，未覆盖或可能冲突哪些（引用文档章节或铁律编号即可）。有冲突时先标风险，再问用户是收敛方案还是上升拍板，不擅自扩展口径。

**怎么说（按 author 柔性适配）**

- 先读当前 author 的 `工作习惯.md`、`沟通偏好.md`、`沟通规范.md`；必要时结合 `learn-user-habits` 的当次观察。
- **详略随人**：负责人 / 架构讨论偏原则对齐与取舍理由；执行 / 工程偏边界、通断与铁律是否踩线；非代码背景成员偏可感知效果与是否偏离项目目标。
- **不强制固定模板**，不每轮刷屏；用户明确「先实现、别展开」时可缩为一句对齐结论；用户要求「对齐顶层设计」「汇报审核」或跨模块变更时必须写清依据与条目。
- 稳定对齐结论写入 task `design.md` 或 `process.md`，便于交接与复盘。

## 协作机制（按需）

### 收件

- 行为约束（启动只读文件头、跨用户发件例外）见 `主流程.md` §2 R9。
- 文件头格式、已处理精简、启动扫描、拍板发件义务 → `project-inbox-rules`。

### 经验整理与公共化

- L0 任务过程 → L1 私人经验 → L2 leader 公共抽取 → L3 硬规则；不能一次任务流水直接升公共规则。
- 分层、积累触发、整理确认 → `personal-experience-curation/references/curation-hard-rules.md`。
- 执行入口 → `personal-experience-curation`。
- 评判标准 → `personal-experience-curation/references/experience-evaluation.md`、`experience-curation-standards.md`。

### 收尾与公共化归属

- 收尾前按 `主流程.md` §4 加载。
- 仅 `tech-lead` 或授权维护者执行公共化；普通 author 在 task `process.md` 记建议。
- leader 公共化写入归属：工具经验 → `工具经验.md`；**团队不变量/协作/设计原则** → `docs/规则/` 对应分册；**团队深层原则** → `项目大脑/公理/`；团队硬规则 → 本文；代码规范 → `docs/规则/` 代码类分册；公共能力 → `skills/`/`mcps/`/`hooks/`。
- `协作灵魂.md`、`沟通规范.md` 属私人软上下文，不在项目大脑根目录建公共版。

## 维护约束

- 新增 skill 触发 → 只改 `主流程.md` §3。
- 新增 L3 硬规则 → `主流程.md` §2 加一行 + 本文写详情。
- 格式/步骤/字段清单 → 只改对应 skill reference。
- 本文修改须用户二次确认；与 `说明.md` 设计思想保持一致。
